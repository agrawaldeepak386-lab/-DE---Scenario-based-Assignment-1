# DE — Scenario Based Assignment 2 (Claims Lakehouse)

This folder contains Assignment 2 of the data-engineering scenario series. It takes the claims lakehouse built in **DE - Scenario based Assignment 1** and turns it into a governed, orchestrated, deployable project:

* **R1 — Access Control Governance** — governance objects (row filter `claims.gov.claims_state_filter`, column masks on PII, admin proof tables) documented in the `R1 Access Control Governance` notebook.
* **R2 — Lineage Evidence** — proof that `claims.raw.members.phone` flows into bronze and silver (`members_clean`, `members_quarantine`) and into the governance proof/masked tables; see `evidence/r2_lineage_answer.md` (with the Catalog Explorer lineage screenshot embedded).
* **R3 — Quarantine Audit** — `src/claims_quarantine_audit.py` + `src/quarantine_rules.py` implement the quarantine rules (Q-A…Q-E, including the date-window rule) used by the silver layer and data-quality checks.
* **R4 — Orchestration** — the daily job chains: setup → pipeline (max 3 retries) → DQ check → gate (`dq_problems == 0`) → gold publish; triggered by file arrival in the raw landing volume.
* **R5 — CLI Evidence** — `evidence/cli/r5_cli_log.txt` records an authenticated CLI session (PAT profile, volume file upload, job run-now / get-run showing SUCCESS).
* **R6 — Declarative Automation Bundle** — bundle `claims_lakehouse` (see `databricks.yml`) deploying the pipeline and job to isolated dev/prod catalogs.

## Bundle configuration

* Two variables decouple reading from writing:
  * `source_catalog` — catalog holding the raw landing volumes (bronze reads here; default `claims`)
  * `target_catalog` — catalog the pipeline publishes bronze/silver/gold into
* Targets:
  * `dev` (default, development mode) → publishes into `claims_dev`; deployed names are auto-prefixed `[dev ...]` and triggers paused
  * `prod` (production mode) → publishes into `claims_prod`
* The pipeline sources its SQL transformations from the sibling folder `../DE - Scenario based Assignment 1/claims_pipeline/transformations/`.

## Deploying

```bash
databricks bundle validate --target dev    # or --target prod
databricks bundle deploy   --target dev
databricks bundle run      claims_lakehouse_daily --target dev
```

## Notes

* Source data lands in `/Volumes/claims/raw/landing/claims/claims_raw/` (the job's file-arrival trigger watches this path).
* The gold layer is published as managed Delta tables (`claims_enriched`, `hospital_monthly`); the `claims.gov.claims_state_filter` row filter is re-applied via `ALTER TABLE` after publish.
* `dq_problems` = number of failing quarantine rules (not the quarantined row count); the gate fails the job when any rule fails.
* `.bundle/` and `.databricks/` are generated by the DAB CLI — never edit them by hand.
